### 2.2 Action `editarEquipeAction` (`equipes/_actions.ts`, nova)

```ts
export async function editarEquipeAction(_prev: State, formData: FormData): Promise<State & { codigo?: string }> {
  const id = formData.get('id') as string
  const codigo = ((formData.get('codigo') as string) ?? '').trim().toUpperCase()
  const motorista_id = (formData.get('motorista_id') as string) || null
  if (!id) return { error: 'ID inválido' }
  if (!codigo) return { error: 'Informe o código da equipe' }

  const supabase = await createClient()
  const erro = await requireGestorFrotas(supabase)          // gestor spec §3.1
  if (erro) return { error: erro }

  const { data, error } = await supabase.rpc('editar_equipe_atomico', {
    p_equipe_id: id, p_codigo: codigo, p_motorista_id: motorista_id,
  })
  if (error) return { error: error.code === 'SOF01' ? error.message : 'Erro ao salvar a equipe' }

  revalidatePath('/sofia/equipes'); revalidatePath('/sofia/motoristas')
  revalidatePath('/sofia/disponibilidade'); revalidatePath('/sofia/audit')
  return { success: true, codigo: (data as { codigo: string }).codigo }
}
```

- **Sem `logAudit`**: a função grava o `audit_log` na mesma transação (não duplica, não perde).
- `requireGestorFrotas` é chamado **antes** de qualquer escrita; o teste jest prova que `rpc('editar_equipe_atomico')`
  não é chamado quando nega.

### 2.3 Função `editar_equipe_atomico` — o que faz e por quê

Por que função e não três UPDATEs na action: são até 5 escritas (código, motorista anterior, motorista novo,
histórico da equipe, histórico da equipe de origem) + auditoria. Território 3 do `AGENTS.md` (sobrescreve dado de
cliente): parar no meio deixaria motorista sem equipe ou histórico apontando para a pessoa errada. Em função, ou tudo
grava ou nada grava.

1. Guarda `sofia_pode_gerir() is not true` → "Apenas administradores ou gestores de frotas podem editar equipes".
2. Código normalizado `upper(btrim(p_codigo))`; vazio → `SOF01` "Informe o código da equipe".
3. Trava a equipe (`for update`); inexistente → `SOF01` "Equipe não encontrada."
4. Código repetido: `exists (... upper(codigo) = v_codigo and id <> p_equipe_id)` → `SOF01` "Já existe uma equipe com o
   código {X}." E o `unique` da coluna é a segunda barreira (corrida entre dois salvamentos): `unique_violation` →
   mesma mensagem.
5. Motoristas atuais = **ativos** com `equipe_id = p_equipe_id` (travados). Motorista novo, se informado, tem de
   existir e estar ativo → senão `SOF01` "Motorista não encontrado ou desativado."
6. Nada mudou (mesmo código e mesmo conjunto de motoristas) → `SOF01` "Nada foi alterado."
7. Efeito nos motoristas (invariante: **no máximo um motorista ativo por equipe** depois de salvar):
   - todos os ativos da equipe, menos o novo, ficam com `equipe_id = null` ("{atual} fica sem equipe");
   - o novo passa a `equipe_id = p_equipe_id`; se vinha de outra equipe X, X fica sem esse motorista
     ("{novo} sai da {X}, que fica sem motorista").
   - Motoristas **inativos** não são tocados (não pedidos; continuam com o `equipe_id` antigo, como hoje).
8. Histórico de responsabilidade (mesmo padrão de `atribuir_responsabilidade_veiculo`, `track-c:157-165`): para o
   veículo não-inativo da equipe, fecha o registro aberto (`fim = current_date`) e abre outro com o motorista novo
   (`origem_checklist_id = null`). Idem para o veículo da equipe X, com o motorista ativo que sobrar lá (normalmente
   nenhum → `null`).
9. **O que impede trocar o veículo por aqui:** a função não recebe veículo e não escreve `veiculos.equipe_id` (a
   verificação nº 10 do SQL confere que o corpo não contém `update public.veiculos`); o formulário não tem campo de
   veículo. O único caminho para trocar carro continua sendo o checklist (`criarChecklistAction` →
   `atribuir_responsabilidade_veiculo`, `checklist/_actions.ts:88-106`) e a tela do veículo
   (`atualizarEquipeVeiculoAction`, `veiculos/_actions.ts:96-123`, admin/gestor pela gestor spec).
10. `audit_log`: `tabela='equipes'`, `operacao='atualizou'`, `registro_id = equipe`, `descricao` legível,
    `usuario_id = auth.uid()`, `usuario_email` do JWT, `dados` = `{tipo:'edicao_equipe', antes:{codigo, motoristas[]},
    depois:{codigo, motorista}, equipe_que_perdeu_motorista, autor}`. Aparece no "Registro de atividades" geral (não no
    "Histórico de correções", que o mockup restringe a KM e abastecimento, `r4hist` `:672`).

Triggers/RLS envolvidos: UPDATE `equipes.codigo` dispara `trg_bloquear_escrita_equipes`, que só olha `ativo` → passa.
`motoristas`, `veiculo_responsabilidade_historico`, `audit_log`: sem trigger; RLS `sofia access` (gestor e admin têm o
slug ou são admin → passam). Nenhum `veiculos` é escrito (só travado com `for update`, que não dispara trigger).

### 3.3 Função `corrigir_km_atomico` — decisões

- **`security invoker`, não definer.** Justificativa:
  - Com invoker, a função **não consegue fazer nada que o usuário já não pudesse** pela RLS `sofia access`; a guarda
    `sofia_pode_gerir()` só **estreita** isso para admin/gestor. Um defeito na guarda não abre o banco para quem não
    tem o slug `sofia` (a RLS ainda barra). Com definer, a guarda seria a única barreira (é o caso de
    `excluir_multas_em_massa`, cuja nota em `track-c:204-206` lembra o custo disso).
  - Não precisa de definer: o gestor tem o slug `sofia` (exigência da gestor spec §1.3), então RLS deixa ler/escrever
    `km_diario`, `veiculos` e inserir em `audit_log`; o admin passa por `sofia_has_access()` (`v04-seguranca.sql:76-77`).
    `sofia_pode_gerir()` em si é definer (lê `sofia_gestores`, sem policy) — a função chama, não precisa ser.
  - Precedente no projeto: `obras_desfazer_diario` é invoker (`.claude/rules/sql.md`, tabela de estado).
  - `lancar_km_atomico` é definer por herança do Track C, não por necessidade; não é mudado aqui.
- **Trava:** lê o `veiculo_id` do lançamento sem trava, depois `select ... from veiculos ... for update` e só então
  relê o lançamento `for update`. Ordem **veiculos → km_diario**, a mesma de `lancar_km_atomico` (`track-c:91-94` e
  depois o upsert), então correção e lançamento do mesmo carro se enfileiram sem deadlock e sem o B-13.
- **Intervalo:** vizinhos do **mesmo veículo** por data (unique `(data, veiculo_id)` garante um por dia): anterior =
  maior data menor; seguinte = menor data maior. `novo >= anterior` e `novo <= seguinte` (igual ao mockup, que compara
  com o vizinho imediato, `s4fixkm` `:682-683`, `:691-692`).
- **Recálculo:** `veiculos.km_atual := max(km_diario.km_atual)` do veículo depois da correção ("maior lançamento
  restante"); só escreve se mudou. Correção de um lançamento do meio não mexe no KM atual (mockup: "continua").
- **Erros legíveis:** regras de negócio com `errcode = 'SOF01'` (a action repassa só esses, como `km/_actions.ts:111`);
  guarda sem errcode (P0001), como as funções irmãs — a action já barrou antes, então o usuário nunca vê esse texto.
  Formatação de número igual à de `lancar_km_atomico` (`track-c:104-105`), data `DD/MM/YYYY`.
- **Auditoria** na mesma transação: `tabela='km_diario'`, `operacao='corrigiu'`, `registro_id = lançamento`,
  `usuario_id = auth.uid()` (do JWT, nunca parâmetro — mesma razão de `track-c:204-206`), `usuario_email` do JWT,
  `dados` = `{tipo:'correcao_km', contexto:{equipe, placa, data, veiculo_id}, antes:{km_atual}, depois:{km_atual},
  km_veiculo:{antes, depois}, motivo, autor:{email, nome, papel}}`. `contexto` guarda equipe/placa **do momento** (o
  código da equipe pode mudar depois por F1). `papel` = `'administrador'` se `sofia_is_admin()`, senão `'gestor de
  frotas'`. `nome` = `user_metadata.full_name` do JWT (mesma fonte de `app/(dashboard)/dashboard/page.tsx:17`).
- **Retorno** `jsonb` `{placa, km_veiculo_antes, km_veiculo_depois}` (jsonb em vez de `returns table` para não criar
  variáveis OUT com nome de coluna).

### 3.4 KM excedido depois da correção (**pergunta ao João**, §8)

Uma correção muda o "KM rodado no mês", que alimenta `km_excedido_desconto` (desconto em salário). Hoje
`verificarERegistrarExcedencia` (`km/_actions.ts:11-74`) só **cria/atualiza** quando há excesso e **retorna cedo** quando
não há (`:32`). Chamá-la depois da correção resolve o caso "corrigiu e ainda excede" (atualiza `km_realizado`), mas
deixa errado o caso típico do Igor — **KM digitado a mais gerou um excesso falso**: a correção tira o excesso e a linha
de desconto fica com o valor velho. Recomendação (aguarda resposta): depois da correção, recalcular o mês do
lançamento; se existir linha em `km_excedido_desconto` com `autorizacao_status = 'sem_solicitacao'`, atualizar
`km_realizado` (mesmo que deixe de exceder); se já estiver `solicitado`/`autorizado`, **não mexer** e mostrar no sucesso
"Este mês tem desconto de KM excedido em andamento. Confira em Descontos." Até a resposta, a action **não** chama nada
de excedência (o comentário no código marca o ponto).

-- ============================================================
-- 1. F2 — corrigir_km_atomico
-- ============================================================
create or replace function public.corrigir_km_atomico(
  p_km_id uuid,
  p_km_novo integer,
  p_motivo text
)
returns jsonb
language plpgsql
security invoker
set search_path = pg_catalog, public
as $$
declare
  v_veiculo_id uuid;
  v_veic record;
  v_lanc record;
  v_ant record;
  v_prox record;
  v_tem_ant boolean;
  v_tem_prox boolean;
  v_km_veiculo_novo integer;
  v_equipe text;
  v_motivo text := nullif(btrim(p_motivo), '');
  v_email text := lower(btrim(auth.jwt() ->> 'email'));
begin
  -- "is not true": sofia_pode_gerir() nunca deve devolver NULL, mas "if not NULL"
  -- não dispara e a guarda falharia ABERTO (.claude/rules/sql.md, armadilha 1).
  if public.sofia_pode_gerir() is not true then
    raise exception 'Apenas administradores ou gestores de frotas podem corrigir lançamentos de KM';
  end if;

  if p_km_novo is null or p_km_novo < 0 then
    raise exception 'Informe o KM correto.' using errcode = 'SOF01';
  end if;

  -- 1ª leitura sem trava: só para saber qual veículo travar. A ordem de trava é
  -- veiculos -> km_diario, a mesma de lancar_km_atomico (sem deadlock, sem B-13).
  select k.veiculo_id into v_veiculo_id
  from public.km_diario k where k.id = p_km_id;
  if v_veiculo_id is null then
    raise exception 'Lançamento de KM não encontrado.' using errcode = 'SOF01';
  end if;

  select v.id, v.placa, v.km_atual into v_veic
  from public.veiculos v where v.id = v_veiculo_id
  for update;

  select k.id, k.data, k.km_atual, k.equipe_id into v_lanc
  from public.km_diario k where k.id = p_km_id
  for update;
  if not found then
    raise exception 'Lançamento de KM não encontrado.' using errcode = 'SOF01';
  end if;

  if p_km_novo = v_lanc.km_atual then
    raise exception 'O valor é igual ao lançado. Nada a corrigir.' using errcode = 'SOF01';
  end if;

  select k.data, k.km_atual into v_ant
  from public.km_diario k
  where k.veiculo_id = v_veiculo_id and k.data < v_lanc.data
  order by k.data desc
  limit 1;
  v_tem_ant := found;

  select k.data, k.km_atual into v_prox
  from public.km_diario k
  where k.veiculo_id = v_veiculo_id and k.data > v_lanc.data
  order by k.data asc
  limit 1;
  v_tem_prox := found;

  if v_tem_ant and p_km_novo < v_ant.km_atual then
    raise exception 'O KM não pode ser menor que o lançamento anterior: % km em %.',
      replace(trim(to_char(v_ant.km_atual, '999G999G999')), ',', '.'),
      to_char(v_ant.data, 'DD/MM/YYYY')
      using errcode = 'SOF01';
  end if;

  if v_tem_prox and p_km_novo > v_prox.km_atual then
    raise exception 'O KM não pode ser maior que o lançamento seguinte: % km em %.',
      replace(trim(to_char(v_prox.km_atual, '999G999G999')), ',', '.'),
      to_char(v_prox.data, 'DD/MM/YYYY')
      using errcode = 'SOF01';
  end if;

  update public.km_diario set km_atual = p_km_novo where id = p_km_id;

  -- KM atual do veículo = maior lançamento restante (diagnóstico §4 opção C).
  select max(k.km_atual) into v_km_veiculo_novo
  from public.km_diario k where k.veiculo_id = v_veiculo_id;

  if v_km_veiculo_novo is distinct from v_veic.km_atual then
    update public.veiculos set km_atual = v_km_veiculo_novo where id = v_veiculo_id;
  end if;

  select e.codigo into v_equipe from public.equipes e where e.id = v_lanc.equipe_id;

  -- usuario_id vem do JWT, nunca de parâmetro: o autor da correção não pode
  -- ser escolhido por quem chama /rpc/.
  insert into public.audit_log (tabela, operacao, registro_id, descricao, usuario_id, usuario_email, dados)
  values (
    'km_diario', 'corrigiu', p_km_id::text,
    format('KM corrigido — %s · %s · lançamento de %s: %s → %s km',
           coalesce(v_equipe, '—'), v_veic.placa, to_char(v_lanc.data, 'DD/MM/YYYY'),
           v_lanc.km_atual, p_km_novo),
    auth.uid(),
    v_email,
    jsonb_build_object(
      'tipo', 'correcao_km',
      'contexto', jsonb_build_object('equipe', v_equipe, 'placa', v_veic.placa,
                                     'data', v_lanc.data, 'veiculo_id', v_veiculo_id),
      'antes', jsonb_build_object('km_atual', v_lanc.km_atual),
      'depois', jsonb_build_object('km_atual', p_km_novo),
      'km_veiculo', jsonb_build_object('antes', v_veic.km_atual, 'depois', v_km_veiculo_novo),
      'motivo', v_motivo,
      'autor', jsonb_build_object(
        'email', v_email,
        'nome', nullif(btrim(auth.jwt() -> 'user_metadata' ->> 'full_name'), ''),
        'papel', case when public.sofia_is_admin() then 'administrador' else 'gestor de frotas' end)
    )
  );

  return jsonb_build_object(
    'placa', v_veic.placa,
    'km_veiculo_antes', v_veic.km_atual,
    'km_veiculo_depois', v_km_veiculo_novo
  );
end;
$$;


-- ============================================================
-- 2. F3 — corrigir_abastecimento (NÃO mexe em veiculos.km_atual: decisão
--    aprovada no mockup — quem define o KM atual é o KM diário)
-- ============================================================
create or replace function public.corrigir_abastecimento(
  p_abastecimento_id uuid,
  p_litros numeric,
  p_valor numeric,
  p_km integer,
  p_motivo text
)
returns void
language plpgsql
security invoker
set search_path = pg_catalog, public
as $$
declare
  v_ab record;
  v_ant record;
  v_prox record;
  v_placa text;
  v_litros numeric := round(p_litros, 2);   -- colunas são numeric(8,2)/(10,2)
  v_valor numeric := round(p_valor, 2);
  v_antes jsonb := '{}'::jsonb;
  v_depois jsonb := '{}'::jsonb;
  v_motivo text := nullif(btrim(p_motivo), '');
  v_email text := lower(btrim(auth.jwt() ->> 'email'));
begin
  if public.sofia_pode_gerir() is not true then
    raise exception 'Apenas administradores ou gestores de frotas podem corrigir abastecimentos';
  end if;

  if v_litros is null or v_litros < 0 then
    raise exception 'Informe os litros abastecidos.' using errcode = 'SOF01';
  end if;
  if v_valor is null or v_valor < 0 then
    raise exception 'Informe o valor do abastecimento.' using errcode = 'SOF01';
  end if;
  if p_km is not null and p_km < 0 then
    raise exception 'KM inválido.' using errcode = 'SOF01';
  end if;

  select a.id, a.veiculo_id, a.data, a.created_at, a.litros, a.valor, a.km into v_ab
  from public.abastecimentos a where a.id = p_abastecimento_id
  for update;
  if not found then
    raise exception 'Abastecimento não encontrado.' using errcode = 'SOF01';
  end if;

  if v_litros is not distinct from v_ab.litros
     and v_valor is not distinct from v_ab.valor
     and p_km is not distinct from v_ab.km then
    raise exception 'Nada foi alterado.' using errcode = 'SOF01';
  end if;

  -- Vizinhos do mesmo veículo que TÊM km (km é opcional). Pode haver dois
  -- abastecimentos no mesmo dia: desempate por created_at e id.
  if p_km is not null then
    select a.data, a.km into v_ant
    from public.abastecimentos a
    where a.veiculo_id = v_ab.veiculo_id and a.km is not null and a.id <> v_ab.id
      and (a.data, a.created_at, a.id) < (v_ab.data, v_ab.created_at, v_ab.id)
    order by a.data desc, a.created_at desc, a.id desc
    limit 1;
    if found and p_km < v_ant.km then
      raise exception 'O KM não pode ser menor que o do abastecimento anterior: % km em %.',
        replace(trim(to_char(v_ant.km, '999G999G999')), ',', '.'),
        to_char(v_ant.data, 'DD/MM/YYYY')
        using errcode = 'SOF01';
    end if;

    select a.data, a.km into v_prox
    from public.abastecimentos a
    where a.veiculo_id = v_ab.veiculo_id and a.km is not null and a.id <> v_ab.id
      and (a.data, a.created_at, a.id) > (v_ab.data, v_ab.created_at, v_ab.id)
    order by a.data asc, a.created_at asc, a.id asc
    limit 1;
    if found and p_km > v_prox.km then
      raise exception 'O KM não pode ser maior que o do abastecimento seguinte: % km em %.',
        replace(trim(to_char(v_prox.km, '999G999G999')), ',', '.'),
        to_char(v_prox.data, 'DD/MM/YYYY')
        using errcode = 'SOF01';
    end if;
  end if;

  update public.abastecimentos
     set litros = v_litros, valor = v_valor, km = p_km
   where id = p_abastecimento_id;

  -- Antes/depois só dos campos que mudaram (é o que o histórico mostra).
  if v_litros is distinct from v_ab.litros then
    v_antes := v_antes || jsonb_build_object('litros', v_ab.litros);
    v_depois := v_depois || jsonb_build_object('litros', v_litros);
  end if;
  if v_valor is distinct from v_ab.valor then
    v_antes := v_antes || jsonb_build_object('valor', v_ab.valor);
    v_depois := v_depois || jsonb_build_object('valor', v_valor);
  end if;
  if p_km is distinct from v_ab.km then
    v_antes := v_antes || jsonb_build_object('km', v_ab.km);
    v_depois := v_depois || jsonb_build_object('km', p_km);
  end if;

  select v.placa into v_placa from public.veiculos v where v.id = v_ab.veiculo_id;

  insert into public.audit_log (tabela, operacao, registro_id, descricao, usuario_id, usuario_email, dados)
  values (
    'abastecimentos', 'corrigiu', p_abastecimento_id::text,
    format('Abastecimento corrigido — %s · %s', v_placa, to_char(v_ab.data, 'DD/MM/YYYY')),
    auth.uid(),
    v_email,
    jsonb_build_object(
      'tipo', 'correcao_abastecimento',
      'contexto', jsonb_build_object('placa', v_placa, 'data', v_ab.data, 'veiculo_id', v_ab.veiculo_id),
      'antes', v_antes,
      'depois', v_depois,
      'motivo', v_motivo,
      'autor', jsonb_build_object(
        'email', v_email,
        'nome', nullif(btrim(auth.jwt() -> 'user_metadata' ->> 'full_name'), ''),
        'papel', case when public.sofia_is_admin() then 'administrador' else 'gestor de frotas' end)
    )
  );
end;
$$;

  end if;

  for update;

    raise exception 'Equipe não encontrada.' using errcode = 'SOF01';
  end if;

   for update;

    for update;
    if v_veic is not null then

    if v_origem is not null then

      from public.veiculos v
      where v.equipe_id = v_origem and v.status <> 'inativo'
      for update;
      if v_veic is not null then

          (veiculo_id, equipe_id, motorista_id, inicio, origem_checklist_id)

             coalesce(v_novo_nome, 'sem motorista'),
             case when v_origem_codigo is not null
                  then format(' (%s ficou sem motorista)', v_origem_codigo) else '' end)

    auth.uid(),
    v_email,
    jsonb_build_object(
      'tipo', 'edicao_equipe',
      'antes', jsonb_build_object('codigo', v_codigo_antes, 'motoristas', to_jsonb(v_atuais_nomes)),
      'depois', jsonb_build_object('codigo', v_codigo, 'motorista', v_novo_nome),
      'equipe_que_perdeu_motorista', v_origem_codigo,
      'autor', jsonb_build_object(
        'email', v_email,
        'nome', nullif(btrim(auth.jwt() -> 'user_metadata' ->> 'full_name'), ''),
        'papel', case when public.sofia_is_admin() then 'administrador' else 'gestor de frotas' end)

end;

## 4. F3 — Corrigir abastecimento (resto da frente)

### 4.1 Trigger atual e o que muda

`trg_bloquear_escrita_abastecimentos` é **`before delete`** (`v04-seguranca.sql:316-319`); UPDATE não passa por ele, e
a RLS `sofia access` permite UPDATE a quem tem o slug. **Nada muda em trigger ou policy.** O que F3 acrescenta é a
função `corrigir_abastecimento` (§3.5, item 2), por três motivos: validação de KM com a linha travada, auditoria na
mesma transação (o `logAudit` do app engole erro, `lib/sofia/auditLog.ts:23-27` — correção sem histórico violaria
"Nada se perde" do mockup), e guarda de permissão também no banco.

Campos corrigíveis: **litros, valor, KM** (mockup `s4fixab` `:726-729`). **Data e posto não** — o mockup só mostra o
posto no subtítulo.

### 4.2 Tela (requisito do mockup, `r4ab` `:651-667`, `s4fixab` `:718-762`)

- `abastecimento/page.tsx` (tabela `:115-147`): nova coluna **KM** entre Litros e Valor (cabeçalho `:121-122`); botão
  **"Corrigir"** antes do ✕ quando `podeGerir`; chip "corrigido" na célula de litros dos já corrigidos (via

  - "Litros *" (step 0.1, hint "Lançado: {X}"), "Valor (R$) *" (step 0.01, hint "Lançado: R$ {X}"), "KM no momento"

## 7. Riscos e o que não deu para verificar

**Não verificado (sem acesso ao banco nesta tarefa):**
- **Schema e triggers de produção iguais aos arquivos.** A seção 0 aborta se faltar coluna, constraint ou se houver
  trigger diferente dos 4 esperados nas 7 tabelas; C14 confere antes.
- **`km_diario.km_atual` existe só por `sdd-sql-feedback-cliente.sql`**, que não aparece na tabela de estado de
  `sql.md` com esse nome (está em "aplicados" como `feedback-cliente`). A seção 0 confere o tipo.
- **Quantas equipes têm dois motoristas ativos hoje** (o checklist não limpa o anterior, `track-c:172-174`). Consulta
  para C14: `select equipe_id, count(*) from motoristas where ativo and equipe_id is not null group by 1 having count(*) > 1`.
  F1 corrige uma equipe quando ela for editada; não faz limpeza em massa.
- **Históricos de KM fora de ordem** (lançamento com data retroativa e KM maior é aceito por `lancar_km_atomico`,
  que só compara com `veiculos.km_atual`). Com vizinhos fora de ordem, a faixa permitida pode ficar vazia e a correção
  ser recusada. Consulta para C14:
  `select veiculo_id from (select veiculo_id, km_atual < lag(km_atual) over (partition by veiculo_id order by data) d from km_diario) s where d group by 1`.
  E veículos com `km_atual` diferente do maior lançamento:
  `select v.id from veiculos v join km_diario k on k.veiculo_id = v.id group by v.id, v.km_atual having v.km_atual <> max(k.km_atual)`.
  A primeira correção num desses carros **reescreve `km_atual` com o máximo** — esperado pela opção C, mas é bom saber
  quantos são antes.
- O teste SQL nunca rodou. `set_config('role', 'authenticated', true)` dentro de `do $$` foi comprovado pelo teste de
  `hub_comunicados` (13/13); `exception when sqlstate 'SOF01'` e a comparação exata das mensagens (`1.000 km`) não.
  **SQL só é verificado rodando.**
- A formatação `to_char(..., '999G999G999')` depende de `lc_numeric`; a de `lancar_km_atomico` foi confirmada em
  produção ("2.214 km", `track-c:19-20`) e esta usa a mesma expressão.
- Textos exatos que o Next mostra para erro não-`SOF01`: as actions devolvem texto próprio, não lançam, então não caem
  na tela genérica de `error.tsx`.

**Riscos do desenho:**
- **R1 — UPDATE direto pela RLS (pré-existente).** Qualquer pessoa com o slug `sofia` consegue, pelo navegador,
  alterar `km_diario.km_atual`, `abastecimentos`, `equipes.codigo`, `motoristas.equipe_id` e `veiculos.km_atual`,
  sem passar pelas funções nem pela auditoria (a linha `(info)` do teste mede isso). F1–F3 não pioram: só acrescentam o
  caminho certo. Fechar exige trigger novo e cuidado com o upsert de `lancar_km_atomico` (um "bloqueia UPDATE de
  `km_diario`" quebraria o relançamento do mesmo dia para o usuário comum). Proposta: `docs/DIVIDAS.md`, a menos que o
  João queira agora (§8).
- **R2 — `audit_log` não é à prova de adulteração (pré-existente).** A policy `sofia access` é `for all`
  (`v04-seguranca.sql:153`): quem tem o slug pode inserir linha falsa, alterar ou apagar linha do histórico pelo
  navegador. O "Histórico de correções" herda isso. Registrar em `DIVIDAS.md`; a correção seria policy só de
  SELECT/INSERT para `authenticated`, mudança que mexe em RLS e não foi pedida.
- **R3 — Nome em "Quem" é autodeclarado.** `user_metadata.full_name` pode ser trocado pelo próprio usuário
  (`supabase.auth.updateUser`). O que identifica de verdade é `usuario_id`/`usuario_email` (do JWT); a tela mostra o
  e-mail no `title` e usa o e-mail quando não há nome.
- **R4 — KM excedido desatualizado** após correção (dinheiro) — §3.4, aguarda o João.
- **R5 — Excluir KM continua sem recalcular `veiculos.km_atual`** (`km/_actions.ts:137`). Fora do mockup (o ✕
  permanece). Registrar em `DIVIDAS.md`; com F2 no ar, o caminho recomendado para o cliente é "Corrigir".
- **R6 — `current_date` do banco é UTC.** O histórico de responsabilidade de F1 grava `inicio`/`fim` com a data do
  servidor; entre 21h e 24h de Brasília cai no dia seguinte. Mesmo comportamento de `atribuir_responsabilidade_veiculo`.
- **R7 — `SOF01` vira HTTP 500 no PostgREST** (pendência documentada em `track-c:50-63`); vale também para as 3 funções
  novas. Só ruído de log; a mensagem certa chega ao usuário.
- **R8 — Deadlock em F1** *(texto corrigido pela revisão, item B2)*. O ciclo real seria com `lancar_km_atomico`: ela
  trava o veículo (FOR UPDATE) e depois grava `km_diario`, cuja FK pega FOR KEY SHARE nas linhas de `equipes` e
  `motoristas`; se F1 travasse equipe/motoristas antes do veículo, as duas podiam se esperar. Por isso a função
  implementada trava **veículos primeiro** (o da equipe e o da equipe de origem, em ordem de id), depois a equipe,
  depois os motoristas (em ordem de id). Se ainda assim ocorrer, o Postgres aborta uma das transações inteira (nada
  fica pela metade) e o usuário vê "Erro ao salvar a equipe" e tenta de novo.
- **R9 — Motoristas inativos** ficam com o `equipe_id` antigo (não tocados por F1, como hoje); `equipes/page.tsx:51`
  pode mostrar um motorista inativo como o da equipe. Pré-existente; fora do escopo.
