## 1. Escopo

**Entra:**

1. Rota nova `POST /api/obras/relatorio-diario`, protegida pelo mesmo segredo do cron da sincronização

4. E-mail HTML + texto, imagem inline (`cid`), um envio por destinatário, via `nodemailer` + SMTP Locaweb.
5. Arquivo SQL do job de cron, **a aplicar manualmente** (não aplicado por esta frente).
6. Correção do plural em `app/obras/painel/_historico.tsx:205`.
7. Extração da leitura das 4 tabelas de `app/obras/painel/page.tsx` para um módulo compartilhado
   (justificativa em §4.1).
8. Variáveis novas documentadas em `.env.local.example` e `docs/infra/variaveis-e-deploy.md`.

**Fica fora (de propósito):**

- Tabela de registro de execuções do envio (exigiria schema — ver pergunta aberta P1 em §13).
- Aviso aos administradores quando o envio falha (decidido: sem aviso).

- Filtro por cliente no e-mail, escolha de mês, comparação "ano anterior": o e-mail é sempre o filtro padrão.
- Descadastro ("não quero mais receber"): quem tem acesso recebe. Para parar, tira-se o acesso.
- Migrar `scripts/enviar-comunicado.mjs` do Resend para a Locaweb: a decisão de 08/10 vale para ele também,
  mas é outra frente (ver §12, R8).
- Captura de tela real (Chromium/puppeteer): descartado no levantamento — exigiria imagem Docker nova.

## 2. Fluxo ponta a ponta

```
08:00 BRT (11:00 UTC)
pg_cron job "obras-relatorio-diario"
  └─ net.http_post → https://hub.manfac.com.br/api/obras/relatorio-diario
       Authorization: Bearer <OBRAS_CRON_SECRET do Vault>, corpo {}, timeout 60 s
         │
         ▼
route.ts (runtime nodejs, SÍNCRONA — sem after(), ver §3.4)
  1. segredo e variáveis SMTP presentes?              não → 503
  2. Bearer confere?                                  não → 401
  3. corpo válido?                                    não → 400
  4. em paralelo, com createAdminClient():
       a. 4 leituras do painel (obras, diário, tarefas, remarcações), paginadas
       b. destinatários (2 consultas)
     qualquer erro                                    → 500, ninguém recebe
     lista de destinatários vazia                     → 500, ninguém recebe
  5. lidoEm = agora (hora de Brasília), hoje = hojeISO()
  6. painel = montarPainel(entrada, { cliente: null, mes: hoje[0..7], cmp: 'prev' })
  7. png = ImageResponse(<ImagemDoPainel/>, 900 × alturaDaImagem(painel)) → Buffer
     qualquer erro                                    → 500, ninguém recebe
  8. se corpo.previa === true                         → 200 image/png (nada é enviado)
  9. destinos = corpo.somentePara ? [ele] : todos
     (somentePara fora da lista de destinatários      → 400, nada é enviado)
 10. um transporter SMTP; para cada destino, sendMail (sequencial, sem retry)
 11. todos enviados → 200 { enviados, falhas: [] }
     alguma falha   → 502 { enviados, falhas: [{ para, erro }] }
```

Toda saída que não é 2xx também faz `console.error('[relatorio-diario] ...', motivo)` — vai para o log do
container no EasyPanel. **Nunca** logar senha, segredo, nem o conteúdo do e-mail.

## 3. Contrato da rota

**Arquivo:** `app/api/obras/relatorio-diario/route.ts`. `export const runtime = 'nodejs'`,
`export const maxDuration = 120` (mesmo padrão da sync; no self-host é só declarativo).

`/api/obras/*` **não** está no `matcher` do `middleware.ts` (conferido: só `/api/conversor-os` e `/api/sofia`)
— a rota fica fora do middleware como a da sincronização. Não mexer no matcher.

### 3.1 Requisição

`POST`, `Content-Type: application/json`, `Authorization: Bearer <OBRAS_CRON_SECRET>`.

Corpo (todos opcionais; corpo vazio `{}` = envio normal do cron):

| Campo | Tipo | Efeito |
|---|---|---|
| `previa` | `true` | Faz tudo até gerar a imagem e devolve o PNG. **Não lê SMTP, não envia.** Serve para conferir a imagem com dado real |
| `somentePara` | string (e-mail) | Envia só para esse endereço. Precisa estar na lista de destinatários do momento (comparação em minúsculas, sem espaços) — assim o segredo não vira um disparador para fora da empresa |

Corpo que não seja objeto JSON, `previa` diferente de `true`/ausente, ou `somentePara` que não seja string → 400.
Com `previa: true`, `somentePara` é ignorado.

**Por que esses dois campos existem** (não foram pedidos): são o meio de provar que funciona (§11) sem
disparar e-mail para o cliente em cada teste. Custam ~10 linhas. Sem eles, cada teste real vai para todo mundo.

### 3.2 Autenticação

Reutiliza `autorizacaoDoCronValida` **importada** de `app/api/obras/sincronizar/route.ts` (já exportada lá).
Não mover para `lib/` — é o segundo uso, não o terceiro (régua do AGENTS.md).

Mesmo segredo, mesmo item do Vault (`OBRAS_CRON_SECRET`): **não é preciso segredo novo** nem no Vault nem no
EasyPanel.

### 3.3 Respostas

| Status | Corpo | Quando |
|---|---|---|
| 200 | `image/png` | `previa: true` e tudo certo |
| 200 | `{ status: 'enviado', enviados: n, falhas: [] }` | todos os envios aceitos pelo SMTP |
| 400 | `{ error }` | corpo inválido, ou `somentePara` fora da lista |
| 401 | `{ error: 'Não autorizado' }` | Bearer ausente/errado |
| 500 | `{ error: 'leitura', detalhe }` / `{ error: 'sem destinatários' }` / `{ error: 'imagem', detalhe }` | falhou antes de qualquer envio — **ninguém recebeu** |
| 502 | `{ status: 'parcial', enviados: n, falhas: [{ para, erro }] }` | ao menos um `sendMail` falhou (os demais seguiram) |
| 503 | `{ error: '<VAR> não configurado' }` | `OBRAS_CRON_SECRET` ou alguma `SMTP_*` vazia (com `previa`, só o segredo é exigido) |

`detalhe` e `erro` levam a mensagem do erro (ex.: `"obras_diario: <mensagem do PostgREST>"`,
`"Invalid login: 535 ..."`), nunca credenciais. Mensagens do nodemailer não incluem senha.

### 3.4 Por que síncrona (e não `after()` como a sincronização)

A sincronização responde 202 e roda em `after()` porque grava o resultado em `obras_sync_execucao`. Aqui
**não há tabela** (sem schema). O único registro consultável do resultado é a **resposta HTTP**, que o
`pg_net` guarda em `net._http_response` (status + corpo) — e ela só existe se a rota responder **depois** de
terminar. Por isso a rota faz tudo antes de responder, e o job usa `timeout_milliseconds := 60000`.

Estimativa: 4 leituras paginadas (~1–2 s) + imagem (~1–3 s) + ~6 envios SMTP sequenciais (~1 s cada) ≈ 10–15 s.

Se o `pg_net` estourar o timeout, a rota **continua** (o handler não observa `request.signal`) e os e-mails
saem; o registro é que fica como "timeout". Aceitável; ver R3.

### 3.5 Registro da falha (sem schema)

O "hub registra a falha" do mockup fica, nesta versão, em dois lugares que já existem:

1. **`net._http_response`** — status e corpo da resposta da chamada do cron. Consulta:

   ```sql
   select r.created, r.status_code, r.content, r.timed_out, r.error_msg
     from net._http_response r
    order by r.created desc limit 5;
   ```

   ⚠️ O `pg_net` apaga linhas mais velhas que `pg_net.ttl` (padrão **6 horas** — **a conferir** no banco com
   `select current_setting('pg_net.ttl', true)`). Ou seja: a falha das 8h some por volta das 14h.
2. **Log do container** no EasyPanel (`[relatorio-diario] ...`). Some a cada redeploy.

`cron.job_run_details` **não serve** como prova: mostra `succeeded` sempre que o `net.http_post` foi enfileirado
(armadilha 2 de `.claude/rules/obras.md`).

Isso **não é** o "registro de execuções do envio, para o administrador consultar" que a nota (c) do mockup
descreveu. Ver pergunta aberta **P1**.

## 4. Leitura dos dados

### 4.1 Painel — extração de `page.tsx`

A leitura das 4 tabelas (função `lerTudo` + `Promise.all` em `app/obras/painel/page.tsx:57-75`) sai para
`app/obras/painel/_leitura.ts`:

```ts
export async function lerEntradaDoPainel(supabase): Promise<
  { ok: true; obras; diario; tarefas; remarcacoes } | { ok: false; erro: string }
>
```

- Mesmas tabelas, **mesmas colunas**, mesma paginação (`lerTodasAsLinhas`, ordem por `id`), mesmo `select('*')`
  em `obras_obra` (o comentário do topo de `page.tsx` explica por quê).
- `page.tsx` passa a chamar `lerEntradaDoPainel(supabase)` com o cliente do usuário; a rota chama com
  `createAdminClient()`. Na tela, `ok: false` mostra o mesmo `EstadoVazio` de hoje.
- `erro` diz qual tabela falhou e a mensagem (a tela não usa; a rota devolve no 500).

**Por que extrair, contra a régua "inline até 3 usos":** o requisito é "mesmos números da tela". Duas cópias
da leitura divergem em silêncio no dia em que alguém acrescentar uma coluna a uma e não à outra, e o e-mail
passa a mostrar número diferente da tela sem ninguém perceber. É mover ~20 linhas, não criar camada.

### 4.2 Filtro

`montarPainel(entrada, { cliente: null, mes: hojeISO().slice(0, 7), cmp: 'prev' })` — exatamente o que a tela
monta sem parâmetro na URL (`page.tsx:97-103`). `hojeISO()` já é dia de São Paulo. Às 11:00 UTC é 08:00 em
Brasília o ano todo (sem horário de verão desde 2019).

No dia 1º, o mês em curso tem 1 dia (`01/MM a 01/MM`) — é o mesmo comportamento da tela às 8h do dia 1º.

### 4.3 Destinatários

Duas consultas pelo cliente admin, em paralelo com as do painel:

```ts
admin.from('hub_system_access').select('user_email').eq('system_slug', 'obras').eq('has_access', true)
admin.from('hub_user_roles').select('user_email').eq('nivel', 'administrador')
```

- `nivel = 'administrador'` é a definição de administrador do hub (`lib/auth/roles.ts`, `isAdmin`), a mesma
  usada pelo `scripts/enviar-comunicado.mjs`.
- `has_access = true` estrito (null/false fora), como `hasSystemAccess`.
- Junção: `trim().toLowerCase()`, descarta vazio, `Set` → array ordenado (ordem estável para teste e log).
  Função pura `montarDestinatarios(linhasAcesso, linhasAdmins)` em `_email.ts`.
- **Qualquer erro em qualquer das duas → 500, ninguém recebe** (território 2 do AGENTS.md: controle de acesso
  falha fechado). Lista vazia → 500.
- Lidos no momento do envio: quem perdeu acesso ontem não recebe hoje.

## 5. A imagem

### 5.1 Técnica

- `ImageResponse` de `next/og` (Satori + Resvg; `@vercel/og` 0.11.1 empacotado no Next 16.2.11 — conferido em
  `node_modules/next/dist/compiled/@vercel/og`). Só flexbox e um subconjunto de CSS; **todo `div` com mais de
  um filho precisa de `display: 'flex'` explícito**; sem `grid`, sem `outline`, sem `box-shadow inset`.
- `const png = Buffer.from(await new ImageResponse(el, { width: 900, height: alturaDaImagem(painel), fonts }).arrayBuffer())`.
  Erro em qualquer ponto (inclusive dentro do stream do `arrayBuffer`) → 500.
- **Altura precisa ser calculada** — o `ImageResponse` exige `height` (padrão 630) e corta o que passar.
  `alturaDaImagem(painel)` soma alturas fixas por bloco + altura fixa por linha das partes variáveis (clientes,
  equipes, motivos de parada, linhas do cronograma). Para isso **toda linha de tabela tem altura fixa e texto em
  uma linha** (`whiteSpace: 'nowrap'`, `overflow: 'hidden'`, `textOverflow: 'ellipsis'`); subtítulos são
  curtos o bastante para caber em 900 px (conferido visualmente em §11).
- **Fontes:** o `next/og` traz só `Geist-Regular.ttf`. O mockup usa Inter (texto) + mono, com negrito. Versionar
  3 TTF estáticos (licença OFL) em `app/api/obras/relatorio-diario/_fontes/`:
  `Inter-Regular.ttf` (400), `Inter-Bold.ttf` (700), `JetBrainsMono-Bold.ttf` (700). Pesos 600/800 do mockup
  viram 700. Lidos com `readFile(join(process.cwd(), 'app/api/obras/relatorio-diario/_fontes/...'))` — o hub
  roda com `next start` sobre o repositório inteiro (sem `output: 'standalone'` no `next.config.ts`), então o
  arquivo existe em produção. Fonte: release oficial de cada família (rsms/inter, JetBrains/JetBrainsMono),
  arquivos estáticos — **não** a versão variável (Satori não lida bem com fonte variável).
- Glifos usados que precisam existir na fonte: `▲ ▼ = — → × · º –`. Os deltas e números vão na mono, como na tela.

### 5.2 Escala

O mockup desenhou a imagem a **1200 px**; o aprovado é **900 px**. Todas as medidas do CSS `.img` do mockup
(fontes, paddings, larguras fixas como os 250 px do rótulo do Gantt) são multiplicadas por **0,75**.
Ex.: corpo 19 → 14 px; número do KPI 32 → 24 px; título 46 → 34 px. Exibida a 600 px no e-mail, o fator total
fica 0,5 — igual ao que o mockup mostrou no computador.

Cores: as do CSS `.img` do mockup, que são as do tema do hub (`#0a1628`, `#0d2050`, `#1e3a5f`, `#94a3b8`,
`#f05a28`, verdes/vermelhos/âmbar do painel).

### 5.3 Bloco a bloco

Ordem e conteúdo = `build()` do mockup. Textos dinâmicos **saem de `painel`** (nunca recalculados); os
formatadores são os da tela (`R`, `K`, `N0`, `N1`, `fd`, `mesCurto` de `app/obras/painel/_ui.tsx`).
"Igual à tela" = mesmo rótulo e mesma regra de `_painel.tsx`; o que muda está dito.

|---|---|---|---|

Janela do Gantt: **a mesma de `montarPainel`** (`cronograma.janela`, 28 dias antes e 42 depois de hoje,

### 5.4 Recorte do cronograma — critério exato

Função pura `recorteDoCronograma(linhas: LinhaGantt[], limite = 7): LinhaGantt[]` em `_recorte.ts`.

Cada linha recebe uma **prioridade** (a primeira que casar):

| Prioridade | Condição (campos de `LinhaGantt`) | Ordem dentro da prioridade |
|---|---|---|
| 1 — atrasada | `atrasada === true` (em campo atrasada ou a iniciar com início planejado vencido) | `diasAtraso` desc |
| 2 — parada | `parada === true` | início (`planIni ?? realIni`) asc |
| 3 — próxima a iniciar | `grupo === 'iniciar'` | `planIni` asc (a mais próxima primeiro) |
| 4 — em campo no prazo | `grupo === 'campo'` | início asc |
| 5 — terminou | `grupo === 'terminou'` | `realFim` desc (a mais recente primeiro) |

Desempate final em todas: `obra.os` asc (determinístico). Pega as `limite` primeiras **nessa ordem** e desenha
nessa ordem (as críticas no topo). Prioridades 4 e 5 só entram se sobrar vaga — é o que faz o estado "quase
vazio" do mockup ainda mostrar obras em campo.

"Mostrando N de M": `N` = tamanho do recorte, `M` = `cronograma.linhas.length` (as obras que a tela desenha
com o filtro "Todas"). Se `cronograma.semDatas > 0`, acrescenta a frase da tela
("K obras ficaram fora do cronograma por não ter início planejado"). Se `M = 0`, o bloco mostra
"Nenhuma obra no cronograma hoje." e altura de vazio.

### 5.5 `alt`

Função pura `textoAlternativo(painel)`:

```
Painel gerencial de DD/MM/AAAA — Carteira R$ X · Faturamento do mês R$ Y · Faturado no ano R$ Z · Pendente faturamento R$ W
```

`X = kpis.carteira.valor`, `Y = kpis.faturamentoMes.valor`, `Z = kpis.faturadoAno.valor`, `W = kpis.pendente.valor`,
formatados com `R()`. Os mesmos 4 números vão no corpo em texto (§6) — quem bloqueia imagem ainda lê o essencial.

### 5.6 "O valor grande do cartão de faturamento cabe"

Pior caso realista: `R$ 99.999.999` em 24 px mono bold num cartão de ~(840 − 3×12)/4 ≈ 200 px de largura útil
menos padding. JetBrains Mono 24 px ≈ 14,4 px/caractere × 13 caracteres ≈ 187 px → cabe no limite. Regra:
`whiteSpace: 'nowrap'`; se `R(valor).length > 12`, a fonte do valor cai para 20 px. Teste em §11 com
`R$ 12.345.678`.

## 6. O e-mail

Funções puras em `app/api/obras/relatorio-diario/_email.ts`; o envio fica na rota.

| Campo | Valor |
|---|---|
| `from` | `"Manfac" <manfac@manfac.com.br>` (constante no código) |

| `html` | §6.1 |
| `text` | §6.2 |
| `attachments` | `[{ filename: 'painel-gerencial-AAAA-MM-DD.png', content: png, contentType: 'image/png', cid: 'painel-gerencial@manfac', contentDisposition: 'inline' }]` |

### 6.1 HTML

Layout em `<table>` (clientes de e-mail não respeitam flex), largura 600, estilos inline, fundo `#e9edf4`,
coluna branca — a "moldura" clara do mockup:

```ts
const transporte = nodemailer.createTransport({
  host: process.env.SMTP_HOST, port: Number(process.env.SMTP_PORT),
  secure: Number(process.env.SMTP_PORT) === 465,   // 465 = TLS direto; 587 = STARTTLS
  requireTLS: Number(process.env.SMTP_PORT) !== 465,
  auth: { user: process.env.SMTP_USER, pass: process.env.SMTP_PASS },
})
```

Um transporter por execução, envios em sequência (`for … of` com `await`), cada `sendMail` num `try/catch`
que só **registra** a falha e segue para o próximo. Sem `pool`, sem retry, sem `verify()` prévio.

```sql
begin

  'obras-relatorio-diario',

select 'job existe, ativo, 0 11 * * *' as invariante,

                          and schedule = '0 11 * * *' and active) then 'OK' else '*** FALHOU ***' end
union all

                          and command like '%/api/obras/relatorio-diario%') then 'OK' else '*** FALHOU ***' end
union all
select 'jobs da sincronização intactos (2)',
       case when (select count(*) from cron.job where jobname in ('obras-field-incremental','obras-field-completa')
                   and active) = 2 then 'OK' else '*** FALHOU ***' end
union all
select 'segredo no Vault',
       case when exists (select 1 from vault.secrets where name = 'OBRAS_CRON_SECRET') then 'OK' else '*** FALHOU ***' end;
```

## 10. Dependência nova

**`nodemailer` versão exata `10.0.10`** (`"nodemailer": "10.0.10"` em `dependencies`, sem `^`).

Por quê essa:

- **Por que nodemailer:** é o cliente SMTP padrão de Node; o `next/og` cobre a imagem, mas nada no hub fala SMTP
  (conferido: sem nodemailer/puppeteer no `package.json`). Escrever SMTP + MIME + `cid` à mão seria muito mais
  código e mais risco.
- **Linha 10:** traz os próprios tipos (`types: ./dist/cjs/nodemailer.d.ts`) — o `@types/nodemailer` mais novo
  é 8.0.2 e não cobre a 10; zero dependências; `engines: node >= 20` (o hub é Node 20, `.nvmrc`).
- **10.0.10 e não a `latest` (10.0.16, 07/10/2026):** a linha 10 saiu em 04/09/2026 e teve 10 versões em 10 dias;
  a 10.0.10 (14/09/2026) foi seguida de 13 dias sem release — é a mais recente com mais de duas semanas de
  estrada e sinal de estabilidade. As 10.0.11–10.0.16 saíram entre 27/09 e 07/10, ritmo de correção ainda alto.
  Nenhuma das versões está marcada `deprecated` no npm (conferido).
- **Antes de instalar:** conferir no GitHub (`nodemailer/nodemailer`, releases/CHANGELOG e security advisories)
  se alguma de 10.0.11–10.0.16 corrige falha de segurança. Se sim, usar a primeira versão que corrige.
  Não deu para verificar o changelog desta máquina sem rede ampla — **item de verificação, não fato**.

Fontes TTF (§5.1) não são dependência npm; são 3 arquivos versionados (~0,3–0,5 MB cada) com o `OFL.txt` ao lado.
