# Investigação — 185 OS (nossa extração) x 25 atividades (contagem do João no Field)

**15/09/2026.** Só leitura na API do Field (GET), com a mesma chave de `.env.local`.
Nenhum código do app foi alterado; nada foi escrito em produção. Os dados usados vêm de
duas fontes: o cache local desta investigação (`ordens-cru-cache.json` e
`tasks-cru-cache.json`, no scratchpad da sessão — não commitados) e um punhado de
chamadas novas, só leitura, para responder o que o cache não tinha (lista de `/services`,
`/work-services`, `/tasks` global, e o campo `archived` de cada atividade).

**Veredito curto: a hipótese de "tipo de atividade diferente de tipo de OS" está
DESCARTADA pelos dados — a API não tem esse campo.** A explicação mais provável agora é
algo na TELA do Field (paginação, busca por texto em vez de filtro estruturado, ou
escopo da conta/equipe) — nenhuma dessas dá para confirmar por API; só o painel do João
confirma. Ver §5.

---

## 1. Que serviço é o nosso `service_id`?

**Não é um valor fixo (env/constante/banco) — é resolvido em tempo de execução, pelo
NOME, a cada varredura** (com cache em memória do processo, não persistido):

- A busca é pelo nome `"Atividade Spot"`, constante `NOME_PADRAO_DO_TIPO_DE_OS`
  (`app/obras/_lib/field/cliente.ts:22`).
- A resolução roda em `resolverIdDoTipoDeOs()` (`cliente.ts:158-173`): chama
  `GET /services?q=name:"Atividade Spot"` e aplica `escolherTipoDeOs()`
  (`cliente.ts:102-127`) para desempatar se vier mais de um resultado.
- A sincronização real não passa `nomeDoTipoDeOs` nem `estrategiaDeLoja` —
  `app/obras/sincronizar/_execucao.ts:190` chama `criarClienteField({ chaveApi })` só
  com a chave, então usa esse padrão.

**O que a API devolve para `/services` (todos os 10 tipos de OS cadastrados, sem
filtro):**

ou tipo ambíguo) está descartada.**

## 2. Como a API chama "atividade" — existe tipo/categoria própria?

**Não existe.** Testado de três formas:

1. **O objeto da atividade** (`GET /orders/:id/tasks`, item do array `items`) tem estes
   campos: `id, duration, position, status, startedAt, completedAt, statusDescription,
   ratingLink, description, viewedAt, receivedAt, archived, createdAt, updatedAt,
   metadata, statusClassification, employee, order, scheduling, coords, startCoords,
   completeCoords`. **Nenhum campo de tipo/categoria/serviço.** O único vínculo com
   "Atividade Spot" é indireto: `order: { id }` aponta para a OS, e é a OS que tem
   `service`.
2. **`GET /work-services`** (o recurso de faturamento com nome parecido, mas
   documentado como *outro* recurso — ver `api-field-control-levantamento.md` §2)
   respondeu 200 com **`totalCount: 0`** — a conta não tem nenhum item cadastrado ali.
   Não é isso.
3. **`GET /tasks`** (endpoint global, não documentado, mas existe e responde 200) —
   testado com quatro filtros diferentes no `q`
   (`service_id:"..."`, `order_service_id:"..."`, `type:"Atividade Spot"`, e um campo
   inventado só para forçar erro): **os quatro devolveram exatamente o mesmo
   `totalCount: 5927`.** Ou seja, **esse endpoint global ignora silenciosamente
   qualquer filtro em `q`** — não é 422, não filtra, só devolve tudo. `5927` é o total
   de atividades da conta inteira, de todos os tipos de OS, e não serve para isolar
   "Spot" por essa via.

**Conclusão provada: uma "atividade" não tem tipo próprio na API — o único jeito de uma
atividade ser "do tipo Spot" é a OS-mãe dela ser do tipo Spot.** Não existe, na API, um
segundo critério de classificação de atividade que pudesse divergir do critério de OS.

## 3. Quantas OS têm pelo menos uma atividade Spot

Consequência direta do item 2: como toda atividade "é Spot" só por herdar da OS, e todas
as 185 OS trazidas pela varredura são do tipo Spot, **as 185 têm, por definição, pelo
menos uma atividade Spot** (nenhuma tem zero atividades — conferido na exportação:
`zeroAtividades: 0`). O total de atividades sob essas 185 OS é **210** (mín. 1, máx. 4
por OS; 164 OS com exatamente 1, 18 com 2, 2 com 3, 1 com 4).

**Nem 185 nem 210 se aproxima de 25 por este caminho.** A hipótese "o filtro dele é por
tipo de atividade, o nosso é por tipo de OS, e são coisas diferentes" não se sustenta,
porque na API eles são a mesma coisa — não existe uma segunda classificação para
divergir.

## 4. O que a listagem NÃO filtra (confirmado com dado)

| Filtro que a listagem NÃO aplica | O que os dados mostram |
|---|---|
| `archived` da OS | **0 de 185** OS vieram com `archived: true` (inclusive a 7777, já reportado antes) |
| `archived` da atividade | Das 210 atividades, **205 `false` / 5 `true`**. Só **2 de 185 OS têm TODAS as atividades arquivadas**, e só **4 de 185 têm a ÚLTIMA atividade arquivada**. Não é um recorte que produza 25 — **hipótese "atividade arquivada explica o sumiço" também descartada** |
| Status da última atividade | Nenhum filtro — a listagem traz todos os status. Contagem real (via `triagem-suspeitas-2026-09-15.md`, gerada sem nova chamada): `Resolvido` 58, `done` 51, `pending` 45, `scheduled` 13, `Orçamento Aguardando Aprovação` 4, `Falta de Tempo` 3, `reported` 2, `Fechar OS` 2, e sete valores únicos (1 cada) — nenhuma combinação simples desses valores fecha em 25 |
| `updated_at` | Não entra na carga completa (`cliente.ts:179-182` + `_execucao.ts:140`) |

**O que ficou provado, sem depender do painel:** o `service_id` que a sincronização usa
é o correto e único "Atividade Spot" (§1); não existe, na API, nenhum campo de
tipo/categoria de atividade que pudesse divergir do tipo da OS (§2); nem `archived` de
OS, nem `archived` de atividade, nem status da última atividade explicam sozinhos uma
queda de 185 para 25 (§4). **O que continua hipótese, e só o painel resolve:** se "25" é
o total real da tela ou só o tamanho de uma página (D), se o filtro usado foi busca de
texto em vez de tipo estruturado (E), e se a tela tem escopo de conta/equipe/período
diferente do da chave de API (F).

**Recomendação:** não puxar nada para produção até D e E serem checados no painel — são
os mais baratos de testar e, se qualquer um deles for a causa, o `service_id` e a
sincronização continuam corretos (nada a mudar no código); só o número "25" que o João
viu estava sendo mal lido, não os 185 da nossa extração.
