Frentes do Controle de Obras

Quem faz o quê, por quê, e em que ordem. O sistema controla obras de manutenção em lojas da rede DPSP: a obra nasce como uma OS no Field Control, a equipe da Manfac responde um diário todo dia, e o sistema acusa quando uma obra para de andar. Esse último ponto é a razão do projeto existir — a obra que ficou 123 dias parada sem ninguém notar.

01

Como o trabalho foi dividido

O critério não é tamanho de tarefa. São três coisas, nesta ordem de peso.

1 · Credencial

O que só uma pessoa consegue executar não é divisível. Supabase, push no GitHub, deploy e a planilha do cliente estão todos atrás de credencial do João.

2 · Canal com o cliente

Frente que depende de decisão do cliente fica com quem fala com ele. Hoje há duas perguntas em aberto, e as duas mudam código.

3 · Sobreposição de arquivo

Duas frentes que editam o mesmo arquivo não rodam em paralelo sem merge doloroso. Este critério gerou a única restrição de ordem deste documento.

03

A única restrição de ordem

Se só uma coisa deste documento for lembrada, que seja esta.

1a e 1b editam o mesmo arquivo

app/obras/obra/[id]/_actions.ts — a Triagem grava lá, e os marcos precisam ser gravados na troca de etapa, que também mora lá. Tocar as duas ao mesmo tempo garante conflito de merge no arquivo mais delicado do módulo.

Por isso o Duda começa pela 1d, não pela 1b. A 1b entra depois que a 1a estiver mergeada. A 1c é código novo em pasta própria e roda em paralelo com qualquer coisa.

João
0 · no ar → 1a · campos editáveis → 1c · Field Control
Duda
higiene → 1d · foto diária → espera merge da 1a → 1b · colunas mortas

A 1c não bloqueia nada e nada bloqueia ela — é código novo em pasta própria. Se o João estiver preso na 1a esperando o cliente, a 1c anda junto.

04

Para o Duda começar

Na ordem. O passo 1 é do João; os outros são dele.

1

Acessos. Supabase da Manfac como Developer — roda SQL, escreve no banco, cria bucket, e não consegue apagar projeto, mexer em cobrança nem convidar ninguém. Mais acesso de escrita ao repositório no GitHub. Convite por e-mail, conta própria — login não se compartilha.

2

Ler antes de escrever qualquer linha. O AGENTS.md na raiz do repositório é a fonte de verdade operacional: infra, deploy, banco, autorização e as armadilhas que já custaram dias. E o ESTADO.md desta frente, que tem o histórico de decisões do cliente.

3

Subir o ambiente e confirmar que o verde bate antes de mudar nada.

# Node 20 (.nvmrc)
npm install
npm run dev      # desenvolvimento
npm test         # jest — espere 204/204 em app/obras
npm run lint
npm run build

Processo — não pule etapas

brainstorming → mockup visual aprovado → spec → plano → código → code review → deploy. Mockup antes de spec ou código, sempre — e interativo quando envolver animação ou interação.

Convenções de código

Server Actions em _actions.ts ao lado da página, formulários em _form.tsx, tabelas em _table.tsx. Prefixo _ não vira rota. Testes em __tests__/ ao lado do código.

Tema

Fundo #0a1628, navy #0d2050, laranja #f05a28, texto secundário #94a3b8, bordas #1e3a5f. Tailwind v4.

Migrations são manuais

Cada mudança de schema vira um arquivo sdd-sql-*.sql na raiz que alguém roda à mão. Código mergeado não significa schema aplicado — confira o banco antes de concluir que um bug é de código.

Material do cliente vira arquivo

Lista, relatório, áudio transcrito, requisito escrito: salvar literal em docs/cliente/ e commitar antes de agir sobre o conteúdo. Sem resumir. O resumo vira spec depois; o arquivo é a fonte.

Segredos

Nunca colar service role key, senha ou chave de API em chat ou em arquivo versionado. Sem exceção.

Uma armadilha que já mordeu neste projeto e vale saber de antemão: o repositório se chama login-system por herança de quando era só a tela de login — hoje ele é o hub inteiro, com quatro sistemas dentro. E manfac-site/ na mesma árvore é o site institucional, com deploy próprio: não faz parte do hub.
